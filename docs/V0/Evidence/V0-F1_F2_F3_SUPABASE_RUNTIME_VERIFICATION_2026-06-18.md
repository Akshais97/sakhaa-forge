# V0-F1/F2/F3 Supabase Runtime Verification Evidence - 2026-06-18

## Scope

Slices:

- `V0-F1` tenant-safe sign-in and workspace selection.
- `V0-F2` executable contracts, errors and idempotency.
- `V0-F3` private artifact upload, quarantine and authorized retrieval.

Behaviour verified:

- API runtime can run in `V0_RUNTIME_DB=prisma` mode.
- `POST /api/v0/workspaces` persists `User`, `Workspace`, `Membership`,
  `AuditEvent` and `IdempotencyRecord` rows in Supabase PostgreSQL.
- Reusing an idempotency key with the same input replays the stored response.
- Reusing the same idempotency key with changed input returns
  `IDEMPOTENCY_INPUT_CONFLICT`.
- Workspace listing reads persisted runtime data.
- Brand-asset upload persists `Artifact`, promotes a matching supported upload to `CLEAN`
  and keeps retrieval workspace-scoped.
- Cross-workspace artifact download returns existence-hiding `WORKSPACE_ACCESS_DENIED`.

## Decision

Runtime database proof is now required for F1-F3 closure. Local simulator evidence remains
useful for deterministic development, but Supabase runtime writes are now verified through
the API.

## Notes

- The test reads `apps/api/.env` but does not print secret values.
- Direct row verification uses `DIRECT_DATABASE_URL` when present, otherwise
  `DATABASE_URL`.
- The API imports the generated Prisma client from `packages/db/generated/client`.
  `packages/db/generated/` is ignored and regenerated by `pnpm db:generate`.
- Earlier migration tooling printed an old database URL before secret-safe preflight
  existed. That database password must remain treated as compromised unless already
  rotated.
